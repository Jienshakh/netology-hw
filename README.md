### Задание 1. СУБД

### Кейс
Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать 
правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для
каждой предметной области. 

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему? 
 
1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков.
СУБД должна гарантировать целостность и чёткую структуру данных.

1.1.* Хеширование стало занимать длительно время, какое API можно использовать для ускорения работы? 

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к 
маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? 
СУБД должны быть гибкими и быстрыми.

1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу 
и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это 
реализовать?

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов 
по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать
со связями.

1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД 
логистов?

1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?

*Приведите ответ в свободной форме.*


**1.1. Бюджетирование проектов, финансовые отчёты, прогнозирование рисков**
Тип СУБД: Реляционная СУБД (PostgreSQL, Oracle, Microsoft SQL Server).

Почему?

- Требуется строгая структура данных, ACID-транзакции, сложные JOIN-запросы для аналитики.
- Поддержка триггеров, хранимых процедур для расчётов.
- Интеграция с BI-инструментами (Power BI, Tableau).

**1.1. Ускорение хеширования***

**API:** Можно использовать Redis (как in-memory key-value хранилище) для кеширования результатов хеширования.
Почему? Redis обеспечивает высокую скорость доступа к данным за счёт хранения в оперативной памяти.

**1.2. Лендинги и CRM**

Для лендингов: Документоориентированная NoSQL (MongoDB, Couchbase).
Почему? Гибкость схемы, быстрая запись/чтение данных о лидах.

Для CRM: Реляционная (PostgreSQL) или гибридная (MongoDB + SQL).
Почему? CRM требует структурированных данных о клиентах и транзакциях.

**1.2. Можно ли закрыть одной СУБД?***

Да, можно использовать PostgreSQL с JSONB для лендингов (гибкость) и классическими таблицами для CRM.
Или: MongoDB (для лендингов) + интеграция с CRM через API.

**1.3. База знаний отдела контроля качества**

Тип СУБД: Графовая (Neo4j) или документоориентированная (MongoDB).
Почему?
- Графовая: если нужны связи между нормативами (например, иерархия правил).
- Документоориентированная: если данные хранятся в виде статей/документов.

**1.3. Использование существующей СУБД***

Да, если есть PostgreSQL, можно создать отдельную схему с таблицами для нормативов.
Или: Использовать MongoDB, если она уже есть в инфраструктуре.

**1.4. Логистика (маршруты доставки)**

Тип СУБД: Графовая (Neo4j) или реляционная с геопространственными расширениями (PostGIS).
Почему?
- Графовая: оптимальна для расчёта маршрутов (алгоритмы Дейкстры, A*).
- Реляционная: если нужны сложные JOIN с данными по закупкам.

**1.4. Подключение отдела закупок***

Лучше отдельная СУБД (PostgreSQL) с интеграцией через API.
Почему? Данные закупок (накладные, поставщики) требуют ACID, а логистика — скорости.

**1.5. Можно ли все задачи решить одной СУБД?***

Да, PostgreSQL.
- Бюджетирование: таблицы + аналитические функции.
- CRM: JSONB для гибкости.
- Логистика: PostGIS для маршрутов.
- База знаний: отдельная схема.

**Но:** Для высоконагруженных лендингов лучше добавить Redis/MongoDB.

### Задание 2. Транзакции

2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы 
транзакция завершилась успешно. Ориентируйтесь на шесть действий.

2.1.* Какие действия должны произойти, если пополнение счёта телефона происходило бы через автоплатёж?

*Приведите ответ в свободной форме.*

**2.1. Пополнение баланса телефона**

1. Старт транзакции (BEGIN).
2. Проверка реквизитов (карта/платёжная система).
3. Списание средств с карты пользователя.
4. Зачисление средств на счёт телефона.
5. Фиксация транзакции (COMMIT), если все шаги успешны.
6. Отправка SMS-уведомления пользователю.

**2.1. Автоплатёж***
Добавляются шаги:

1. Проверка лимитов/настроек автоплатежа.
2. Планирование (если дата платежа не сегодня).
3. Повторная попытка при ошибке (с уведомлением).

### Задание 3. SQL vs NoSQL

3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL. 

3.1.* Какие, на ваш взгляд, преимущества у NewSQL систем перед SQL и NoSQL.

*Приведите ответ в свободной форме.*

**3.1. Преимущества SQL**

1. ACID-транзакции — надёжность.
2. Строгая схема — целостность данных.
3. SQL-стандарт — универсальность.
4. Сложные JOIN — аналитика.
5. Зрелость — проверенные решения (Oracle, PostgreSQL).

**3.1. NewSQL***

- Плюсы перед SQL: Горизонтальное масштабирование (как NoSQL).
- Плюсы перед NoSQL: Поддержка ACID и SQL-синтаксиса.
- Пример: CockroachDB, Google Spanner.

### Задание 4. Кластеры

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу 
выделено 1000 машин. 

На основе какого критерия будете выбирать тип СУБД и какая модель *распределённых вычислений* 
здесь справится лучше всего и почему?

*Приведите ответ в свободной форме.*

**Критерии выбора СУБД:**

1. Распределённость (шардирование, репликация).
2. Поддержка параллельных вычислений (MapReduce, Spark).
3. Отказоустойчивость (Paxos, Raft).

Модель распределённых вычислений:

Apache Spark (in-memory обработка).
Почему? Оптимизирован для больших данных, поддерживает SQL, MLlib.

Тип СУБД:
NewSQL (CockroachDB) или NoSQL (Cassandra) + Spark для аналитики.
